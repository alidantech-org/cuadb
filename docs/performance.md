# Large-table performance (1,000,000 rows)

Measured by `tests/performance_live.rs` on a developer laptop (Fedora, local Docker databases, loopback), release not required (dev profile). Table `perf_big(id pk, grp, payload md5 text, created_at)` with 1,000,000 rows on each engine (fixtures: `tests/fixtures/perf.sql`, `perf-mysql.sql`; SQLite is generated by the test). Wall time of the full HTTP request through the router. Reproduce with `cargo test --test performance_live -- --nocapture --test-threads=1`.

| Request | PostgreSQL 18 | MariaDB 11.8 | MySQL 8.4 | SQLite |
|---|---|---|---|---|
| First page (25 rows, ~35 KB) | 28 ms | 31 ms | 36 ms | 5 ms |
| Deepest page (100 × 100, offset 10,000, ~120 KB) | 16 ms | 7 ms | 18 ms | 6 ms |
| Sort `id` desc (indexed) | 310 ms | 3 ms | 4 ms | 3 ms |
| Sort `payload` asc (unindexed, top-N) | 342 ms | 399 ms | 987 ms | 681 ms |
| Literal filter, no match (full scan, all columns) | 476 ms | 1.0 s | 1.7 s | 1.0 s |
| Structure / Indexes + stats | 7 ms / 1 ms | 8 ms / 1 ms | 8 ms / 2 ms | 1 ms / 0 ms |
| Export one page (100 rows) | 7 ms | 3 ms | 6 ms | 3 ms |
| Export relation (capped at 10,000 rows, ~0.6 MB) | 428 ms | 390 ms | 397 ms | 368 ms |
| 100 ms query timeout on a full scan | **504 in 114 ms** | **504 in 104 ms** | **504 in 106 ms** | **504 in 104 ms** |

Findings
- Response size is independent of table size: pages are bounded (checked within 3× between first and deepest page) and exports stop at the row/byte caps.
- Row counts never use `COUNT(*)`; the footer uses engine estimates.
- Server-side abort works on all four engines. MySQL/MariaDB previously only abandoned the query client-side; `max_execution_time` / `max_statement_time` are now set per session, and error codes 3024/1969 map to a 504.
- Fixed while measuring: the "NULLs last" sort wrapper (`ORDER BY (col IS NULL), col`) prevented index use, turning an indexed SQLite sort from ~3 ms into 4 s and MariaDB 3 ms into 206 ms. It is now only added for nullable columns.
- Known cost: the filter casts every column to text and scans the table (0.5–1.7 s at 1M rows); it is bounded by the query timeout. PostgreSQL sorts `id` desc in ~310 ms rather than using the index backwards (not investigated further).
- Not measured: concurrent load, memory use under load, tables far above 1M rows, remote database latency.

## Pagination mode by engine
- **PostgreSQL:** keyset ("seek") paging with scoped, tamper-checked cursors when the relation has a single-column integer unique key and no sort/filter; otherwise offset paging.
- **MySQL, MariaDB, SQLite:** offset paging only (max 100 pages of up to 100 rows, so 10,000 rows deep); ordering is the primary key (rowid for SQLite) so pages are stable but later pages cost O(offset).
- Past 10,000 rows use filters/sorts, or the capped export; there is deliberately no deeper random access.
